# CRM — главный источник данных, своя EspoCRM у каждого Заказчика

Клиенты, Беседы, Заявки, Записи, Автомобили, Заказ-наряды, Сметы, База знаний и Задачи человеку живут в CRM. У нас остаётся только технический буфер в Postgres: принять сообщение от Meta без потерь, не обработать его дважды, повторить отправку. Так сотрудники автосервиса работают в одном месте, а нам не нужно синхронизировать две копии одних и тех же данных.

## Considered Options

- **Своя база — главная, CRM получает копию** (как в MVP: Заявка уходит в Google-таблицу и CRM-webhook). Отклонили: для статуса ремонта, свободных слотов и дат ТО пришлось бы держать две копии и мирить их.
- **Своя self-hosted CRM** — выбрали EspoCRM: польский язык, календарь, задачи, свои сущности, REST API. Twenty отклонили: тяжелее, а календарь и задачи в ней не подтвердили.
- **CRM Заказчика** подключаем только если у неё есть API. Иначе Заказчик работает в нашей EspoCRM. Выгрузку файлов и разбор почты как замену API не делаем: у польских программ для автосервисов API часто нет.

## Consequences

- Каждому Заказчику своя EspoCRM, ядро (n8n, Ассистент) общее. Данные автосервисов не смешиваются, это проще для RODO, но серверов больше.
- Код говорит с CRM через один переходник. Под каждую CRM Заказчика пишется свой.
- Google-таблица и Telegram как Каналы доставки в целевой схеме уходят.
